## 当前机制摘要

### 请求与空间排程

玩家经营模拟 AI 服务。用户通过 IM（即时通信）提出请求，每次请求对应唯一的不规则任务块。任务先进入候选区，合法放入可用格子后开始运行。模块可按 90° 旋转；摆放不得越界、重叠或占用未开放格子。

任务独立推进，增加并发数量不会自动平分其他任务的既有速度。具体 token/s 采用最新确认的算力与架构决定机制。内存面积、架构轮廓与速度的耦合关系仍需细化，不能把原案“架构只管轮廓”当成完整定义。

区域内移动保持进度；拖拽时原位置仍占用并运行，合法落下后转移，非法落下恢复。撤回释放空间并保留计算进度。能力累计和计频余量的保留规则原案列为建议，尚需确认。换模按最新规则使所有任务回候选区，具体逐状态处理见待定清单。

### 计算、质量与交付

原案同时记录计算进度和多项能力累计。模型按配置周期添加能力，达到计算终点时立即冻结结果；逐能力判档后取最低质量档。至少区分未达标、完成、优秀。算完不等于质量达标。

算完后停止本轮忍耐、继续占格；玩家点击后释放空间并结算，再进入对话。重复点击不得重复收费。原案规定超时移除模块，按已完成 token 结算；完成与截止同刻时按及时完成处理。

原案用计算量与计费 token 分离的建议建模。最新 token/s 规则提出后，两者的单位、映射及终点处理需统一。不能未经确认将二者直接等同，或另加不在原案中的资源。

### 对话、语料、训练与模型

每次交付继续对应用户会话。回复选择可影响关系、群体声望、剧情和语料。原案确定对话产出带来源的语料，训练模块占据摆放空间，完成后产出新模型；模型可另存、命名和切换。

最新确认将训练列为核心，模型属性由对话语料经训练形成。直接加点、天赋专精、内存奖励与训练的分工必须重新明确，不将现有加点实现自动视为正式训练规则。

模型卡片展示全部信息，名称可改，稳定 UUID 只在卡片右下角小字显示。不要新增复制或详情按钮。模型保存的含义与整局磁盘存档是两件事，不能混称已经完成。

### 扩容、阶段、政策与方案

原案设置初始 1 根内存、再加装 4 次，共五档容量；内存扩大可用面积，架构影响区域轮廓。最新确认另有五个发展阶段和 1/2/4 阶段架构解锁，**不能未经确认将阶段等同内存档位**。

保留固定方案工作台、横向政策树和群体声望的原案方向。自由连线流程编辑器不做；格子经验未采纳；小模型路由推迟。现有九节点能力树只是实现骨架，不是完整政策内容的替代。

### 经营与叙事

原案包含按 token 的 API（应用程序编程接口）计费与 Token Plan（词元额度套餐），由政策解锁，可共存。月度维护费、一个月欠费宽限及还不上欠款的失败结局仍在原案范围内。任务收入即时入账或月底到账、套餐超额和质量收费后果仍待定。

特殊用户方向包括工程师、恋爱者、友商蒸馏相关用户与科研学者。常规结局平均游玩约 2 小时是原案目标，不代表现有内容量和平衡已经达到。真实大模型联网调用不属于本体交付。

### 交互与视觉

采用最新确认的瑞士风格与极简方向，并参考下载的 `双击试玩.html` 中动效。用户已接受封面 A 并要求去掉草稿标识，干净 PNG/SVG 已交付。原案黑白手绘属于源版本视觉记录，不应覆盖后续视觉确认。

暂停保持其他交互正常；换模时所有任务回候选。原案主动暂停冻结所有时钟、管理模态阻断操作等旧定义须按新规则复核，不能从既有代码反推设计。

游戏定位与主要决策

已确定：游戏采用实时空间排程与经营玩法，支持主动暂停。请求来自 IM（Instant Messaging，即时通信）窗口，以可旋转的不规则模块表示。模块合法放入区域后自动运行。

各任务独立推进，并发不分摊已有任务的基础速度。暂停冻结游戏时间；扩大区域可容纳更多请求和训练任务。

玩家需要决定请求的处理顺序，通过旋转和移动容纳更多模块。必要时可撤回正在运行的任务，为紧急请求让位。任务完成后，玩家还需选择如何回复用户。

完整游戏包含扩容、模型训练和架构选择，也包含固定方案工作台、群体声望、政策和剧情结局。小模型路由推迟，邻接与格子经验尚未采纳。

制作分为基础任务闭环、成长系统和叙事内容。游戏中的发展阶段及其历史映射暂缓定案。

已确定：一次用户请求对应一个任务模块。计算结束后出现提示，玩家点击确认完成任务，才能继续相应对话；一个长期会话可以产生多轮请求。

建议采用：每个窗口同时最多有一个未终结请求。上一轮完成或失败后，先处理反馈，再产生下一轮请求。长期对话可以包含多轮请求，每轮分别生成任务模块。

请求的完整流程

1. 请求到达。独立 IM 窗口显示需求，生成唯一任务模块，以弹射动画送入候选区。忍耐从请求到达时开始计时。

2. 等待安排。玩家查看形状、总计算量、剩余等待时间、计费方式和当前已解锁的质量风险提示。待处理请求不增长计算或能力进度。

3. 放入区域。合法摆放成功后自动开始计算；非法摆放不占用新位置，不创建额外任务。

4. 独立运行。任务推进自身计算量；当前负责模型按配置频率向该任务添加各类能力点。其他并发任务不分摊其基础速度。

5. 移动或撤回。同一区域内可移动和旋转。拖拽时，任务仍在原位置运行；合法落下后才转移。撤回释放空间，并保留计算进度。能力累计和计频余量的保留方式待确认。

6. 计算结束并判质。达到总计算量时，立即按各项能力累计判定质量，取最低质量档，并冻结结果。此时停止忍耐，模块继续占格，显示完成提示。玩家点击后才移除模块、释放空间并结算，随后进入回复。算完的任务仍可能质量不达标。

7. 回复用户。确认后回到对应 IM 会话，回复选项不再倒计时。部分任务提供拒绝或不同风格的回复选项，影响关系、群体声望、剧情和语料。语料随对话生成，并记录来源。

8. 超时失败。截止时仍未算完，请求失败。系统停止计算、移除模块，按已完成 token 结算，并应用关系或群体声望变化。完成与截止同刻发生时，按及时算完处理。已算完待点击的模块不再超时。

建议采用：超时后进入“失败反馈”对话状态，与成功回复区分。反馈结束后，用户可以离开，也可以产生后续请求。

任务状态与计时

| 状态 | 计算与能力进度 | 忍耐倒计时 | 玩家操作 |
| --- | --- | --- | --- |
| 候选待安排 | 不增长 | 继续 | 查看、旋转、放入 |
| 运行中 | 独立计算，按频率积累能力 | 继续 | 移动、旋转、撤回 |
| 已撤回 | 计算保留且停止；能力保留细则待确认 | 继续 | 重新放回 |
| 已算完待确认 | 停止，质量已判定，仍占格 | 停止 | 点击完成提示 |
| 已提交待回复 | 已释放并结算 | 停止 | 回复或选择分支 |
| 已失败待反馈 | 固定为超时时状态 | 停止 | 查看账单及失败反馈 |
| 全局暂停 | 游戏内进度与时钟冻结 | 冻结 | 允许哪些编辑操作待细化，换模型要求暂停 |

已确定的计时与操作边界：

忍耐时间从请求到达开始，包含队列等待、运行和撤回后的等待，撤回不重置截止时间。

计算结束停止本轮忍耐；待确认与回复选项不另设倒计时。模块在点击前继续占格，不能靠拖延点击继续补充能力或改变质量。

区域内合法移动与旋转不丢失进度，也不因拖拽暂停全局时间。

以实际计算完成时刻判断是否赶上截止时间；同刻算完按及时处理，随后等待点击确认。

每个请求只能结算一次；待确认、已提交与已失败状态均不能通过复制、重复点击或重新入场收费。待确认模块是否允许移动仍待确认。

换模型必须先暂停。暂停统一冻结游戏时间、计算、能力积累、忍耐和来客生成。管理页面是否自动暂停、暂停时能否重新摆放、装机时机，均待细化。

请求状态、账单与对话反馈必须一致。已终结请求不能再次运行。

模块摆放与独立计算

已确定：模块可旋转，放入区域后自动开始运行；开启的任务可在同一个区域内移动，撤回时保留进度。

摆放规则：面积、形状与总计算量独立配置。任务可以难摆但算得快，也可以好摆但占用久。基础原型采用统一计算速度。格子约束如下，镜像功能暂不纳入。

区域以可用格子集合表示；边界之外、不可用格子和其他任务占用格子均不能摆放。

模块以相对格子集合表示，旋转为90度增量，不加入镜像操作。

拖拽期间原合法位置继续占用并运行；合法落下时一次性转移占用，非法落下回到原位置。

撤回必须通过明确操作提交，成功撤回后释放空间、暂停该任务计算；重新放入继续原进度。

运行中的旋转也须满足完整合法摆放条件。

每个请求记录总计算量 C、已完成计算量 P、基础速度 v，以及各能力累计值 A。有效运行 Δt 后，进度更新为 P = min(C, P + v × Δt)。

候选、撤回、全局暂停和已算完状态均不推进计算。模型按配置频率增加 A，详见下一节。基础原型统一使用 v，以 C 区分耗时；面积与 C 独立配置。

已确定：其他任务数量不影响本任务的基础速度。扩容增加并发空间，本身不加快单个任务。

可选后续设计：模型或架构可提供独立速度修正，具体效果尚未确定。此类修正仍须保持任务独立运行。

多能力累计与质量分档

已确定：任务记录计算进度和各项能力进度。模型按一定频率添加自身能力点。计算结束时立即停止运行，按当时累计值判定各项质量，再取最低档作为最终质量。至少区分完成和优秀两层标准。

状态使用“已算完”“待确认”，质量使用“未达标”“完成”“优秀”。算完但质量未达标，与超时分别处理；其收费、反馈和语料后果待配置。

| 字段 | 含义 |
| --- | --- |
| C 与 P | 总计算量与已完成计算量；P 达到 C 触发判质 |
| v | 独立计算速度 |
| f 与 m[k] | 模型能力触发频率，以及每次增加的第 k 类能力点 |
| A[k] | 请求已经累计的第 k 类能力 |
| L[k] 与 E[k] | 第 k 类能力的完成门槛与优秀门槛，E 高于 L |
| q[k] 与 Q | 每类质量档与最终质量档 |

判定方式：每次触发时，A[k] 增加当前模型的 m[k]。P 达到 C 后，对任务要求的每类能力分别判档：

A 低于 L：未达标。

A 达到 L、尚未达到 E：完成。

A 达到 E：优秀。

最终质量 Q 取各项档位的最低者。比较对象是质量档，不能直接比较不同能力的原始点数。未被任务要求的能力不参与判定。门槛数值尚未确定。

示例：任务总计算量为100，基础速度为每秒10计算量。模型每秒提供写作6点、代码3点。假定运行10秒，且计入终点同刻的触发，则累计写作60点、代码30点。以下数值仅演示判档。

| 能力 | 完成门槛 | 优秀门槛 | 结束时累计 | 本项质量 |
| --- | --- | --- | --- | --- |
| 写作 | 40 | 60 | 60 | 优秀 |
| 代码 | 20 | 40 | 30 | 完成 |

最终质量为“完成”。写作超额不能弥补代码不足，等待点击也不再增加能力。终点同刻的触发顺序仍是建议，尚待确认。

风险情报已确定：早期只能大致判断风险。政策天赋逐步提高信息精度，后期显示百分比。百分比表示门槛达成度还是结果概率，尚未决定。

建议采用：当前累计规则没有随机机制，因此显示预计门槛达成度，并注明按当前模型和方案估算。早期使用定性提示或分段条；精确累计值和阈值随天赋开放。

换模型建议，未定案：保留 P、各项 A 和计频余量。换模型只改变恢复后新增的点数，旧贡献保持不变。不同模型由此可接力补齐能力。

是否允许接力、主区域换模是否影响全部在途请求，仍需确认。

加速建议，未定案：临时算力同步提高计算速度和能力频率。这样能缩短耗时，并大致保持能力贡献。只加快 P 会提前结束任务，减少累计能力，可能降低质量。

例如，任务原本运行10秒，每秒得1点，门槛为8点。只将计算速度翻倍，5秒结束时仅得5点。若采用这种速度与质量的交换，应在方案效果中明确说明。

实现边界建议，未定案：

频率按有效运行时间累计。暂停和撤回冻结计频余量，移动不重置；恢复或换模不额外触发一次。

能力触发与计算终点同刻时，先记能力，再判质量。长帧越过终点时，按实际完成时刻截断。

训练模块是否设置能力门槛仍待确认。应检查初始模型的成长路径，避免零代码模型无法训练出代码能力。

词元计量与结算

本节的“结算”指确定任务账单。任务结算与月结的到账口径尚需统一：收入是即时入账，还是月底到账，仍待确认。月度收支汇总与维护费结算按月进行。

已确定：

已算完任务由玩家点击确认后，统一移除模块、释放空间并结算。任务质量在算完时已经固定，点击等待不改变质量。

超时失败，按已完成 token 计算 API 售价；Token Plan 则扣除对应 token 额度。

超时仍影响关系与声望，部分收费不等于请求成功。

建议采用：基础原型将“计算量”和“已完成 token”分别记录。计算量衡量需要运行多久，token 衡量计费。不同请求以后可以使用不同计算量与 token 比例。

计量建议：用 floor(T × P / C) 估算已完成 token。T 为预计总计费 token；算完时记 T，超时取失败时累计值。该公式是游戏内估算规则，不代表现实推理的计量方式。质量档是否修正收费待定。

| 结果 | API 计费 | Token Plan 计量 | 状态 |
| --- | --- | --- | --- |
| 算完待确认 | 暂不结算任务账单 | 暂不扣量 | 已判质量，仍占格 |
| 点击确认 | 按完成 token 形成账单 | 扣对应 token，不重复形成 API 账单 | 释放空间并回复 |
| 超时 | 按超时时完成 token 结算 | 扣对应已完成 token | 失败并影响关系与声望 |
| 未开始即超时 | 0 | 0 | 仍为失败 |
| 仅撤回 | 不终结账单 | 不终结账单 | 保留进度，忍耐继续 |

API 与 Token Plan 通过政策树开放，可以同时提供。API 单价、套餐价格和额度待配置。超额处理、输入 token 计费，以及低质量结果是否退款或减收，也尚未确定。

建议采用：每个请求记录一种结算渠道，避免同时按两种方式收费。

用户反馈与群体声望

已确定：客群按最终词条划分，数量待内容设计。各群体有独立声望，影响对应来客比例。某类用户增多，会产生更多对应语料，进而影响模型专精。

保留少量其他类型来客，为玩家提供转向机会。具体客流权重待配置。

建议采用：每名用户归属一个主要群体，基础原型先配置少量群体。群体声望与个人关系分开，复杂个人好感系统稍后制作。

请求配置成功或失败的反馈，对声望应用一次增减。变化在对话窗口和汇总界面可见。

完成速度、回答质量和满意度保持概念上的区别：

速度决定能否在忍耐窗口内完成。

模型提供的能力在运行中累计，计算结束时决定完成或优秀等质量档。

用户反馈可以综合质量、是否按时和回复选择。

基础原型可用固定模型验证质量分档。声望初值、上下限、增减幅度和客流权重待配置，低质量结果的后果也需细化。风险百分比必须与能力累计规则一致；随机成功机制尚未定义。

内存安装与容量里程碑

已确定：内存负责可用面积，架构负责区域轮廓，模型负责专精。模型专精由训练语料的各类分数形成。

四次加装作为重要里程碑。初始内存是否用于安装教程、每阶段的面积和价格，以及对应剧情位置，均待配置。

安装体验方向：购买内存后，打开独立安装页。下压左侧时右端翘起，调整右侧时左端回弹，中间难以直接压入。最终卡扣锁止，发出清脆的“咔哒”声。

内存条保持刚性，以整体倾斜和卡扣动作表现安装过程。

建议采用：小游戏保持短小，成功同时提供卡扣闭合、声音及视觉确认。扩容优先逐级包含原有格子，使在途任务无需搬移。一次安装可依次呈现锁止、自检、新格子开放、扫描线减弱和阶段对话；演出顺序、耗时和与剧情的对应尚未确认。

采用多架构时，应为各架构配置容量阶段对应的轮廓，不能仅凭五档内存就默认全游戏只有五套布局。新旧开放格子是否包含、换架构时在途模块如何安置仍待设计。装机与工作台的关联已确定，是否自动暂停及具体时机尚未定案。

任务运行示例

本例用于核对摆放、计时和账单，数值仅供演示。测试空间为可用区内的一块4×3矩形。实际主界面仍采用正方形总范围、中央不规则开放区。

基础速度为每秒10计算量，API 每 token 计1演示币。算完时停止忍耐，点击后释放空间、结算。本例不预设质量优秀；质量分档见前文示例。

| 请求 | 模块形状 | 总计算量 | 预计 token | 到达时刻 | 忍耐时间 |
| --- | --- | --- | --- | --- | --- |
| A | 2×2 | 100 | 100 | 第0秒 | 20秒 |
| B | 1×3 | 100 | 100 | 第0秒 | 12秒 |
| C | 2×3 | 50 | 50 | 第2秒 | 7秒 |

第0秒，A 与 B 同时放入区域，分别独立以每秒10计算量运行。第2秒，A 进度20、B 进度20；C 到达。玩家将 B 撤回，B 保留进度20并释放格子。将 A 移到左上方，再将 C 放到右侧空位，这两项摆放均合法。

第7秒，C 运行5秒后算完并立即判质，显示完成提示。玩家立即点击确认，释放6格，并按本例费率形成50币账单，用户 C 进入回复。第8秒，B 重新放入并继续原进度。若玩家未提交 C，C 所占空间仍不可用。

第10秒，A 总计运行10秒后算完、判质并显示提示；玩家点击确认，按本例费率形成100币账单，用户 A 进入回复。B 从第8到第12秒运行4秒，累计进度达到60。第12秒，B 到达截止仍未算完，判定超时，清除模块，按60个完成 token 形成60币账单，应用声望损失并显示失败反馈。

本例核对的结果：

A 没有因 B 或 C 同时运行而变慢。

移动 A 没有清空进度，撤回 B 没有重置进度或忍耐时间。

C 的空间与处理优先级来自玩家选择。

B 部分收费，但状态仍为失败。

计算结束、玩家确认和用户回复是三个阶段；本例在确认时结算，回复后才继续相应对话。

语料训练、模型管理与月度经营

已确定的整体方向：

语料随对话生成，并追踪到具体对话。记录包含语料质量和领域分数，如 RP（Role-playing，角色扮演）和代码分数。后期高质量内容通常提供更多点数。记录单位采用消息、轮次还是会话片段，仍待定义。

四次内存加装扩大容量，并与工作台进展关联。扩容对维护费的影响待配置。私奔等特殊结局和失败结局可以提前触发。

小模型路由推迟，不作为本轮规则和当前交付的前提。

训练细则待定：语料是否消耗、能否复用、重复投入的收益，以及基础模型继承方式。分数到能力的映射、训练形状和耗时、取消处理也需细化。当前模型能力是否影响训练，尚未决定。

主题与结局方向

本届主题为“涌现”。基础原型先验证空间排程，主题表达还依赖成长系统与长期关系。独立计算、扩容和旋转提供操作框架，后续反馈循环决定玩家形成怎样的模型与经营方向。

主题设计可沿两条方向展开：

1. 能力成长：接单和回复影响声望，声望改变客群，客群改变语料分布。训练形成模型专精，再影响下一轮经营。固定方案工作台关联发展阶段和扩容，具体顺序暂缓。

2. 用户关系：反复服务与长期交流，逐渐产生超出最初工作目标的行为与关系，再通过经营安排影响剧情结果。

保留恋爱私奔、竞争和经营政策等结局方向。具体人物数量、事件链和触发条件待定。现实供应商名仅作创作参考，不代表企业事实或已确定的结局名称。

历史结论：这些能力并非按唯一顺序发展。代码专精产品早于 New Bing，检索增强研究也早于 Copilot。2018年模型已参与常识推理评测，2024年的节点是强化复杂推理。旧技术仍可与新技术并存。

游戏化推断：研发路线可从续写与角色互动开始，依次发展代码专精、检索与工具流程，最后进入复杂推理或科研。这是游戏所经营服务的路线，不是完整科技史。

代码语料改善代码能力有现实依据。“因此想到接搜索 API”可作为拟人化剧情，由工作台和工程师事件提供接入方案。模型能力变强，本身不会提供网络、API 凭证或执行环境。

本体用数据和规则模拟搜索、训练与推理。研发方案改变可用内容，训练改变模型专精，处理方案调用已有能力。具体阶段与方案职责仍待讨论。

基础原型应优先验证下列闭环；训练、政策、月结和剧情按上表分阶段接入：

至少两个独立 IM 用户窗口可以分别产生请求，并显示对应状态。

一个请求只生成一个模块，进入下方候选区；弹射动画不改变计时和模块唯一性。

旋转与摆放只能占用当前开放格子，不越界、不重叠，也不能进入外层未解锁空间。

两个任务同时运行时各自速度不因并发而下降。

区域内移动不丢失进度；非法落位恢复原位置。

撤回释放空间、保留进度；放回后继续运行。

待处理与撤回状态不能重置忍耐时间。

算完立即判质、停止忍耐并继续占格；点击才释放并结算，重复点击不重复收费，回复选项不继续忍耐计时。

超时移除模块，按完成 token 结算，应用关系或声望反馈。

回复或失败反馈结束后，窗口能够继续后续对话。

建议新增质量检查：多能力取各自门槛对应的最低档，算完后不能继续加能力；主动暂停不能推进时钟。基础原型可先用固定模型，完整游戏再接训练、政策和月结。

# 当前 IM 操作约定（2026-10-17）

IM 历史、普通对话和剧情窗口均非模态。窗口自身接收输入，窗口外仍可拖动、旋转运算模块；升级、模型等真正模态页继续阻挡工作区。候选与棋盘模块左键双击打开所属同一会话窗口，拖拽阈值触发后的手势不算双击。

普通请求算完后在聊天中直接选择回复，选择时复用原提交、质量结算、奖励、语料和下一轮链路；不再要求独立提交按钮。未完成运算只可查看，不可选回复跳过运算。训练任务保留现有训练完成入口。

打开、关闭、切换、提交和重开任何当前对话都不改变手动暂停，也不产生阅读剧情暂停原因或标签。运行中打开仍运行，手动暂停时打开仍暂停。详细层级和输入规则见 [UI-WINDOW-LAYERS.md](UI-WINDOW-LAYERS.md)。本节取代旧文中阅读/待回复阻断工作区或暂停时间的描述。
