# 游戏 QA：功能证据与体验验收分工

目标是让功能更完整、玩家操作更顺畅，而不是增加测试数量。以最新获批需求为验收依据；旧场景测试若已过时，标记需求变化交开发更新，不能为了保住旧断言阻止新功能，也不能把真实回归当成过时测试删掉。

## 角色与权限

- 制作人/root：确定本轮目标与风险、协调开发和 QA，审阅真实操作录像/亲自试玩，负责手感、节奏、视觉和叙事判断。用户保留最终方向决定权。
- 快速 QA 子代理：消费稳定候选，观察、操作测试副本、记录证据、复现、定向回归。不编辑产品代码/场景/Prefab，不偷偷改预期，不自行发布、不覆盖用户存档。写 QA 报告和截图不算产品修复。
- 开发代理：按已授权缺陷修复源码和资产，交付新候选及改动清单，不能以自己的自测代替 QA 复核。修复与 QA 可同模型但须分离任务、证据与结论。
- 可选模型路由为已有的 `magpie/deepseek/deepseek-flash`。先核实路由可用；不可用则报告并使用已授权替代。不能宣称它是最新 DeepSeek，也不能宣称已调用、安装或生效，除非有实际证据。
- 用户电脑只经已核实连接的既有执行线程操作。断线不换机器绕行。遇到权限拒绝停止该动作，不以“QA”名义绕过。测试使用独立存档/候选；不可避免影响用户正在进行的会话时先交制作人决定。

## 每轮流程

1. **交接稳定候选**：记录路径或站点版本、commit/build、分辨率、引擎/浏览器、变更、验收要求、测试存档、允许操作。构建仍被修改时先定版，不把不同版本证据混成一次通过。用 `references/templates.md` 的交接模板。
2. **选风险**：先看本轮 diff 与已知缺陷，选一条核心玩家旅程和一条最可能被影响的邻接路径。除发布里程碑或广泛底层修改外，不反复全量跑所有场景。具体菜单见 `references/player-journeys.md`，只挑相关项。
3. **快速冒烟→真实操作→有目标探索**：先确认能启动/继续；再按鼠标键盘实际路径操作。探索围绕一个问题，例如“弹窗关闭后是否恢复正确暂停状态”，不做无目的乱点。直接注入结束标志或调用内部完成函数不能算真实旅程通过。
4. **记录缺陷**：保存最短复现、预期来源、实际结果、build、截图/录像/日志、发生频率和影响。事实、推测、体验建议分开。重现不稳定时记首次证据，不谎报稳定复现。
5. **开发修复→受影响路径回归**：在新版本重走原复现，再查相邻一条风险路径；新问题则重新分级，不无休止扩大本轮范围。
6. **制作人体验交接**：给出可直接进入的测试点和一段短录像/截图，列出需要主观判断的问题，如 RAM 两端翘起是否易读、拖拽阻尼是否迟滞、剧情停顿是否自然。QA 可以描述现象和提出建议，不能宣布“已经好玩/美型”。

## 有界预算与停止条件

默认一次变更批次：2 分钟交接，3 分钟冒烟，10 分钟相关旅程/探索，5 分钟报告；不是每次必须用满。每个缺陷最多做首次出现后两次复现；捕获可靠证据即可交开发。长旅程超预算时使用已存在、来源标明的阶段存档，或者报告缺口交制作人分配专项窗口，不暗中修改经济/剧情标志来冒充自然进展。

启动即失败、存档有破坏迹象、权限/连接阻塞：停止受影响路径，保留证据，继续可独立进行的项目。预算耗尽时交付已测范围与剩余风险，不将未测项判通过。完成约定风险路径且没有新的阻断问题后，结束本轮，等待新构建或反馈，不重复刷相同结果。

只在修复需要定位计算边界、保存一致性或稳定复现时调用针对性代码测试；已存在便宜的检查可以复用，不为整齐覆盖率新建庞大框架。反复手动出现且高价值的检查再交开发自动化。测试断言与当前已批准需求冲突时，提交“需求变化/用例失效”证据，由开发更新用例，保留资金、存档和操作完整性等仍适用的不变量。

## 结论标准

- S0：存档破坏、严重不可逆数据损害。阻断受影响发布。
- S1：无法启动/继续、主旅程卡死、关键选项不可达、重复扣款/奖励等。阻断相关功能交付。
- S2：重要功能可绕过但操作明显受阻、编辑与运行内容不一致导致无法正常维护。需要修复优先级判断。
- S3：不影响理解与操作的轻微呈现问题。可带已知问题交制作人。

严重度与修复优先级分开：制作人结合当前目标排期。状态只用“通过本轮已测范围 / 有缺陷 / 阻塞 / 未测 / 待制作人判断”。编辑器静态检查、离屏渲染、代码测试、真实 UI 操作分别写明，任何一种都不能冒充另一种。
